# 喂模型调整策略

## 目标与边界

目标是用 `server/resource/full_data` 的原图改进脚部定位，最终让自动生成的谜面更稳定地包含目标人物的双脚，并减少误检和过大的裁切。训练实验与游戏运行完全隔离：本策略不修改游戏题库格式、已上线题目、`catalogue.json`、现有推理模型或游戏服务。新模型只有在独立验收通过且明确决定切换后，才进入单独的集成阶段。

`server/resource/question_data/*.json` 的 `originalImage` 指向原图，`question` 是游戏谜面在原图上的像素裁切范围，包含 `x`、`y`、`width`、`height`、`sourceWidth`、`sourceHeight`。它是可供标注员参考的候选区域，不是天然正确的脚部真值。部分题目由旧模型自动生成，裁切被刻意放大；`enabled` 仅表示题目是否可进入游戏，不表示训练标签已审核。

## 数据隔离

建议在项目外建立独立训练工作区，例如 `D:\arkfeets-foot-training`。所有脚本对 `full_data` 和 `question_data` 只读；标注、导出的训练集、检查点、评估报告和可视化结果均写入训练工作区。不要将大规模训练产物、数据集副本或试验模型提交到游戏仓库。

```text
D:\arkfeets-foot-training\
  annotations\          # 人工确认的原图脚部标注
  datasets\             # 按模型格式导出的训练/验证/测试集
  runs\                 # 检查点、指标、预测预览
  manifests\            # 数据划分、版本、来源和审核记录
```

训练工具不得写回 `question_data`，不得自动注册或启用题目，不得覆盖 `foot_detect/foot_track_net.tflite`。原图路径应通过配置传入，避免在训练脚本中硬编码游戏资源目录。

## 标注设计

以原图为单位标注，不以题目为单位。同一原图可能对应多道题；同一人物的不同皮肤也可能高度相似。每张图记录原图文件名、实际尺寸、文件哈希、审核状态和目标人物的脚部标注。优先分别标注 `leftFoot` 与 `rightFoot` 的紧贴矩形框；确实只有一只脚可见时标明可见性，不要编造另一只。无脚、严重遮挡、模型误把衣物或道具当脚的图片也应保留为困难或负样本。

建议的训练侧标注示例（不是游戏题目 JSON 的新格式）：

```json
{
  "originalImage": "example.png",
  "imageSha256": "原图文件的64位十六进制SHA-256摘要",
  "sourceWidth": 2048,
  "sourceHeight": 2048,
  "reviewStatus": "approved",
  "target": "main-character",
  "feet": [
    { "side": "left", "x": 820, "y": 1750, "width": 90, "height": 140, "visible": true },
    { "side": "right", "x": 980, "y": 1760, "width": 95, "height": 135, "visible": true }
  ]
}
```

首批标注可以把现有 `question` 框显示为参考建议，但必须由人工移动、缩小并确认脚框。不要把 `question` 框直接当作双脚框，也不要仅凭 `enabled: true` 纳入训练。导出前校验图片存在、哈希未变、声明尺寸与实际尺寸一致、坐标非负且不越界、审核状态为 `approved`。同一原图的多个已审核候选发生冲突时应人工处理，不静默择一。

## 两条模型路线

### 路线 A：独立脚部检测模型，优先推荐

如果只有脚框标注，训练单类别 `foot` 检测器最直接。可使用具有预训练权重的目标检测模型，训练数据从独立标注导出为所选框架的格式。以 YOLO 检测格式为例，每个脚框一行 `0 cx cy w h`，四个坐标均除以原图宽高，归一化到 `[0, 1]`；一图两只脚通常产生两行。训练时保留原图尺寸、缩放和填充的映射信息，推理结果必须正确映射回原图像素坐标。

模型输出两个脚框后，单独的训练侧后处理可以复用游戏当前的双脚中心与扩大裁切规则做离线比较；不要让训练程序直接改写题库。若只把现有 `question` 转成单个框，训练目标应明确命名为“谜面区域”，不能把它称为脚检测，也不能期望输出左右脚。

### 路线 B：继续微调 FootTrackNet

当前 `foot_track_net.tflite` 是量化推理产物，不是本项目的训练检查点。若必须继承它的权重，应从官方 PyTorch 模型结构及对应 `.pth` 预训练权重开始，建立与其人物/脸检测、17 个关键点和可见性输出相匹配的训练标签、损失函数与训练循环。只有 `question` 矩形框不足以监督这些输出。微调后的 PyTorch 模型先评估，再导出新的推理文件，并逐项核对输入归一化、输出张量、量化参数和现有解码逻辑。不要假定新 `.tflite` 可以直接替换同名文件。

路线 B 的工程成本和标注量明显更高。只有在获得足够的人物框、踝关节点等真值，并确认路线 A 无法满足目标时再实施。

## 数据划分与训练

1. 固定一版人工审核的数据快照，记录原图哈希、标注版本、来源和审核人。未经审核的自动框只用于预标注，不参与正式训练与测试。
2. 按人物或角色分组划分训练、验证、测试集；同一原图的所有题目和同角色的近似皮肤不得跨集合。测试集在调参期间保持封存。
3. 先建立当前 FootTrackNet 加现有裁切规则的基线，再用相同测试集评估新模型。优先补充失败清单中的不同画风、姿势、遮挡、透明背景和小人物样本，避免只收集容易识别的正例。
4. 从小批量训练和可视化检查开始；记录模型权重来源、随机种子、训练配置、数据快照和每次运行指标。针对类别不平衡及小脚目标做增强，但增强后的脚框必须同步变换。
5. 保留原模型和所有历史题目不变。新模型可以离线跑全量原图，仅输出建议框和报告，不自动覆盖已有裁切。

## 验收与切换门槛

验证不以“检出框数量”或诊断阈值模拟成功率为唯一指标。至少统计：双脚均被正确包含的图片比例、单脚可见场景的正确率、误把衣物/道具/他人脚当目标的比例、裁切面积占原图比例、无脚图误检率，以及失败清单的净改善。按画风、人物大小、遮挡和背景透明度分别看结果，逐图保存新旧模型对照预览。发布门槛应在训练前确定，并以封存测试集上相对现有基线的改善为准。

只有通过验收并明确批准切换，才另立游戏集成任务：新增可回退的模型适配器、运行配置与少量回归测试，先在离线批处理中试用；绝不在训练结束时自动替换游戏模型、批量修改谜面或启用题目。切换失败时保持当前推理与题库原样可用。

## 建议实施顺序

- [ ] 建立只读数据扫描与标注候选导出工具，校验原图和现有 `question` 坐标。
- [ ] 建立独立的双脚标注及审核流程，先完成覆盖成功、失败和负样本的小规模样本集。
- [ ] 固定按角色分组的数据划分与现有模型基线报告。
- [ ] 优先训练路线 A，输出独立检查点和测试集逐图对照。
- [ ] 根据验收结果决定继续扩充标注、尝试路线 B，或另行批准游戏侧集成。
